# Reactive Omni integration

Use the Omni contract library pinned to a reviewed commit in M1. Lasna chain ID is 5318007; fund deployment with lREACT and post reaction reserves separately. Register the CovenantReactive contract itself through the Omni system contract `0x8888888888888888888888888888888888888888` using `subscribe(uint256,address,uint256,uint256,uint256,uint256)`. Use `unsubscribe` with the identical filter. Restrict `react(LogRecord memory)` to the system, recheck chain, emitter and topic signature, and strictly decode the expected indexed fields and data. Track subscription configuration and check live registration. Deploy the Reactive contract first, deploy receiver contracts pinning it, then configure immutable or one-time verified routes and register exact emitters. Keep routing inactive until configuration and funding checks pass. [Omni contracts](https://dev.reactive.network/reactive-contracts), [official library](https://github.com/Reactive-Network/reactive-lib-omni)

Request callbacks with `requestCallbackV_1_0((uint256,address,uint64,bytes))` for chain ID, recipient, gas limit and ABI payload. Encode an address-zero placeholder first; the proxy pathway injects the originating Reactive contract address. Every ingress checks both the exact destination proxy as msg.sender and the exact injected CovenantReactive address. Use distinct receivers for gas billing, especially on Unichain. Pin proxies from [network evidence](NETWORK_VERIFICATION.md). The emitters and receivers below are deployment-specific Covenant addresses.

Topic0 is Keccak-256 of the exact signature. In the initial per-deployment subscriptions use `REACTIVE_IGNORE` for topics 1–3, and decode and validate all three. Agreement-specific deployments may pin topic1. Event integers decoded from topics must fit their ABI widths. Route subscriptions once per deployment; repeated logs never create a new operation ID. Stage transport metadata for bounded retries on Lasna; canonical sink state determines execution. Proofs are separately submitted to the sink by anyone holding the required signatures.

Harness risk updates atomically invoke the Base sampler after updating the position, emitting `RiskObserved` in the same transaction when the bound crosses the threshold. It requires no subsequent user call to initiate the draw. For a live market, candidate triggers include price updates or periodic sampling through an independently verified scheduler, and market account mutations. Aave `Borrow`, `Repay`, and `LiquidationCall` expose relevant changes; a position can deteriorate with no account-specific log. A price trigger requires checking the actual aggregator emitter and validating event shape and feed freshness. Keep third-party subscriptions outside the harness until a particular market, emitter and risk discovery mechanism are verified. [Aave pool interface](https://github.com/aave-dao/aave-v3-origin/blob/main/src/contracts/interfaces/IPool.sol), [Chainlink consumption](https://docs.chain.link/docs/consuming-data-feeds)

Base execution recomputes the entire draw using local authoritative state. Require active signed consent, confirmed collateral, solvent caps, live epoch, fresh prices and acceptable sequencer status, genuine current distress, matching target debt, positive useful repayment, and successful postflight. The adapter may spend less than the offered limit; only net matched spend and applied repayment become principal. Market risk calculations must account for scaled debt rounding and interest; match trusted return data and token movement and validate the resulting state with explicitly tested rounding tolerance. Fund with only the maximum authorized amount and clear allowance.

## Delivery, recovery and funding

Treat delivery as duplicate-prone, arbitrarily delayed and possibly absent. Reactive consensus finality is separate from external source finality. No source-depth SLA, message-order SLA or application-level redelivery guarantee was verified. Use independently authenticated finalized proofs for lock and release. Base-to-Base risk callbacks treat a reorged/unknown epoch as ineligible. Lag and outages fail closed.

Read system `getCallbacks(uint256)` by reactive transaction hash, destination receipt, proxy `CallbackFailure`, and protocol event/state. A successful proxy-level transaction or empty callback record proves no application outcome by itself. For failed funding or execution, correct the cause and request the same semantic operation. Lasna retry uses a stored authenticated payload, fixed receiver, cooldown and per-operation/global attempt cap; a scoped operator can renew bounded attempts after auditing destination state. Durable source lock/release reannouncement is permissionless, rate-limited and emits the same canonical facts. Public Base `executePending` provides an independently guarded fallback. Expired risk epochs require fresh observation. Never alter a consumed intent to force success. Source reannounce handlers must emit only from stored facts and respect local state, including closed release approvals.

Maintain lREACT reserves for subscriptions/reactions and native ETH reserves on each callback proxy for its own destination receiver, using the applicable `depositTo(address)`. Measure receiver gas including proxy overhead for each route and use limits above the documented 100,000 floor. Size draw callback for worst-case adapter path separately from lock/release, record gas and balances per attempt, and budget repeated failures. Insufficient recipient funding/debt can suppress delivery; failed callbacks can still cost gas. See [economy](https://dev.reactive.network/economy), [callback authentication](https://dev.reactive.network/callback-contracts), and [diagnostics](https://dev.reactive.network/debugging).
